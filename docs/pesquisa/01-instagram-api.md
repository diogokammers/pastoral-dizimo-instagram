## 1. Instagram API with Instagram Login vs Instagram API with Facebook Login

- **Fato:** A variante "Instagram API with Instagram Login" **não exige** uma Página do Facebook vinculada. — Fonte: https://developers.facebook.com/docs/instagram-platform/overview (trecho: "Your app serves Instagram professional accounts with a presence on Instagram only")
- **Fato:** A variante "Instagram API with Facebook Login" **exige** que a conta profissional do Instagram esteja conectada a uma Página do Facebook. — Fonte: https://developers.facebook.com/docs/instagram-platform/overview (trecho: "your app users' Instagram professional accounts must be connected to a Facebook Page")
- **Fato:** Confirmação adicional, na própria página do "Instagram API with Instagram Login": "This API setup does not require a Facebook Page to be linked to the Instagram professional account." — Fonte: https://developers.facebook.com/docs/instagram-platform/instagram-api-with-instagram-login
- **Fato:** Ambas as variantes exigem conta profissional (Business ou Creator) — não funcionam com conta pessoal. — Fonte: https://developers.facebook.com/docs/instagram-platform/overview (trecho: "An Instagram professional account can be for a business or creator")
- **Fato:** Com Instagram Login o token é do tipo "Instagram User"; com Facebook Login o token é "Facebook User or Page". — Fonte: https://developers.facebook.com/docs/instagram-platform/overview
- **Fato:** Permissões (Instagram Login, escopos atuais pós-migração de nomes): `instagram_business_content_publish` (publicar conteúdo) e `instagram_business_basic` (leitura básica/insights). — Fonte: https://developers.facebook.com/docs/instagram-platform/instagram-api-with-instagram-login (trecho: escopos citados na página, com nota de que substituem versões legadas descontinuadas em 27/01/2025)
- **Fato:** Permissões (Facebook Login) mencionadas na documentação: `instagram_basic`, `instagram_content_publish`, `instagram_manage_insights`, além de `pages_show_list` e `pages_read_engagement` (necessárias para localizar/ler a Página conectada). — Fonte: https://developers.facebook.com/docs/instagram-platform/instagram-api-with-facebook-login/business-login-for-instagram (trecho: "the list of permission you request will depend on which APIs your app relies on"; fluxo descrito passa por `GET /me/accounts`)
- **Fato:** Para comentários, o escopo é `instagram_business_manage_comments` (Instagram Login) ou `instagram_manage_comments` (Facebook Login). — Fonte: https://developers.facebook.com/docs/instagram-platform/comment-moderation/

## 2. Development vs Live, Standard vs Advanced Access, Instagram Tester, App Review

- **Fato:** Standard Access é o nível padrão de todos os apps e é voltado a apps usados apenas por pessoas com papel no app, durante desenvolvimento/testes. — Fonte: https://developers.facebook.com/docs/instagram-platform/app-review/ (achado via busca, conteúdo da própria doc de App Review)
- **Fato:** Advanced Access é necessário quando o app atende contas profissionais do Instagram que o desenvolvedor **não** possui/gerencia, incluindo usuários sem papel no app; exige App Review e **Business Verification**. — Fonte: https://developers.facebook.com/docs/instagram-platform/app-review/
- **Fato:** Quando o app serve exclusivamente um negócio que o desenvolvedor possui/gerencia (caso da Pastoral, com Diogo como único usuário/admin), **App Review não é necessário**, independente de usar Instagram Login ou Facebook Login, desde que o app permaneça em Standard Access. — Fonte: https://developers.facebook.com/docs/instagram-platform/app-review/ (resumo obtido diretamente da página oficial via fetch)
- **Fato — Verificado em 2ª rodada** (WebFetch direto em https://developers.facebook.com/docs/development/build-and-test/app-roles): a página oficial genérica de App Roles **não menciona "Instagram Tester"** como papel — os papéis listados literalmente são: Administrator, Developer, Tester, Consumer tester, Analytics user. O texto só confirma que convites são enviados "by using the **Roles** section of the Meta App Dashboard" (ou via Business Manager), sem detalhar um submenu "Instagram Testers". Para consumer testers, o aceite é feito em "Settings & privacy > Your activity > Apps and Websites" da conta do Facebook. **Isso contraria a suposição da 1ª rodada** — o papel "Instagram Tester" pode estar em uma página específica do Instagram Platform (não a genérica de App Roles) ou ter sido renomeado/substituído no fluxo atual. Ação recomendada: abrir manualmente o App Dashboard de um app Instagram para confirmar o nome e o caminho exatos do papel de teste antes de contar com ele no planejamento. Mantido como **NÃO VERIFICADO** o caminho exato de menu para o papel de teste específico do Instagram.
- **Fato:** Modo Development com Standard Access consegue operar (publicar/ler insights) nas contas de usuários que têm papel no app (admin, developer, tester/Instagram Tester), sem precisar sair do modo Development, pois Standard Access é justamente descrito como "intended for apps that will only be used by people who have roles on them, during app development, or for testing your app". — Fonte: https://developers.facebook.com/docs/instagram-platform/app-review/ (paráfrase direta da doc)

## 3. Content Publishing (imagem única e carrossel)

- **Fato:** Imagem única: `POST /{ig-user-id}/media` com `image_url`, seguido de `POST /{ig-user-id}/media_publish` usando o `creation_id` retornado. — Fonte: https://developers.facebook.com/docs/instagram-platform/content-publishing
- **Fato:** Carrossel: criar cada item com `POST /{ig-user-id}/media` e `is_carousel_item=true`; depois criar o container do carrossel com `media_type=CAROUSEL` e `children` (lista de IDs dos itens); depois `POST /{ig-user-id}/media_publish`. — Fonte: https://developers.facebook.com/docs/instagram-platform/content-publishing
- **Fato:** Carrosséis são limitados a 10 itens (imagens, vídeos, ou mix). — Fonte: https://developers.facebook.com/docs/instagram-platform/content-publishing (trecho: "Carousels are limited to 10 images, videos, or a mix of the two"). O mínimo de 2 itens é a prática usual do Instagram, mas **NÃO VERIFICADO** literalmente como "mínimo 2" na doc consultada.
- **Fato:** Formato de imagem: apenas JPEG é suportado. — Fonte: https://developers.facebook.com/docs/instagram-platform/content-publishing (trecho: "JPEG is the only image format supported. Extended JPEG formats such as MPO and JPS are not supported")
- **Fato:** A mídia precisa estar hospedada em servidor publicamente acessível no momento do envio: "the media must be hosted on a publicly accessible server at the time of the attempt." — Fonte: https://developers.facebook.com/docs/instagram-platform/instagram-api-with-instagram-login/content-publishing (verificado em 2ª rodada, WebFetch direto). A condição explícita de "sem redirecionamento" **continua NÃO VERIFICADA** — não apareceu no texto extraído desta página nem em `.../ig-user/media`.
- **Fato:** Proporção: no carrossel, as imagens são recortadas com base na primeira imagem, com padrão 1:1. — Fonte: https://developers.facebook.com/docs/instagram-platform/content-publishing (trecho: "Carousel images are all cropped based on the first image... default being a 1:1 aspect ratio"). **Verificado em 2ª rodada** (WebFetch direto em `.../instagram-api-with-instagram-login/content-publishing`): a seção "Limitations" dessa página só repete a exigência de JPEG e de hospedagem pública — a faixa 4:5 a 1.91:1 amplamente citada por terceiros **continua NÃO VERIFICADA**, não aparece no texto extraído. Mantido como NÃO VERIFICADO (ver riscos).
- **Fato:** Limite de tamanho em bytes e largura mín/máx **continuam NÃO VERIFICADOS** mesmo após 2ª rodada — o fetch direto em `.../instagram-api-with-instagram-login/content-publishing` não trouxe esses números na seção "Limitations" extraída (só JPEG e hospedagem pública). Pode ser um bloco renderizado via JS/tabela não capturado pelo extrator; recomenda-se abertura manual no navegador antes de fixar o pipeline de imagem.
- **Fato:** Há suporte a `alt_text` (texto alternativo/acessibilidade) no endpoint `/media` para posts de imagem; não suportado para Reels e Stories. — Fonte: https://developers.facebook.com/docs/instagram-platform/content-publishing (trecho: "New alt_text field for image posts on the /media endpoint. Reels and stories are not supported"). **Verificado em 2ª rodada** direto em `.../ig-user/media`: "Alternative text, up to 1000 character, for an image. Only supported on a single image or image media in a carousel. Reels and stories are not supported." — limite de **1000 caracteres** confirmado literalmente.
- **Fato:** Suporte a `user_tags` (formato `[{username:'ig_user_name'}]`) e a `location_id` no endpoint `/media`. — Fonte: https://developers.facebook.com/docs/instagram-platform/content-publishing. **Verificado em 2ª rodada** direto em `.../ig-user/media`: `user_tags` é "An array of public usernames and x/y coordinates for any public Instagram users who you want to tag in the image" (x obrigatório para imagens, opcional para stories; y de 0.0–1.0); `location_id` é "The ID of a Page associated with a location that you want to tag the image or video with", **não suportado em itens de carrossel**.
- **Fato:** Limite de caracteres de legenda, número máximo de hashtags e de @menções — **Verificado em 2ª rodada**, WebFetch direto em https://developers.facebook.com/docs/instagram-platform/instagram-graph-api/reference/ig-user/media: "A caption for the image, video, or carousel... Maximum 2200 characters, 30 hashtags, and 20 @ tags." Confirma literalmente os números: **2.200 caracteres, 30 hashtags, 20 @menções**. Também confirmado: `caption` não é suportado em itens individuais de carrossel (`is_carousel_item`).
- **Fato (novo, 2ª rodada):** `media_type` é obrigatório para carrossel, story e reel, com valores possíveis `CAROUSEL`, `REELS`, `STORIES`. `children` aceita até 10 IDs de containers para o carrossel publicado. `image_url`: "We will cURL the image using the URL that you specify so the image must be on a public server." — Fonte: https://developers.facebook.com/docs/instagram-platform/instagram-graph-api/reference/ig-user/media (verificado em 2ª rodada, WebFetch direto).
- **Fato:** Status do container é verificado via `GET /{ig-container-id}?fields=status_code`, com valores possíveis `FINISHED` (pronto para publicar), `IN_PROGRESS`, `ERROR`, `EXPIRED` (não publicado em 24h) e `PUBLISHED`. — Fonte: https://developers.facebook.com/docs/instagram-platform/content-publishing
- **Fato:** Limite diário: "Instagram accounts are limited to 100 API-published posts within a 24-hour moving period." Consulta via `GET /{ig-user-id}/content_publishing_limit`. — Fonte: https://developers.facebook.com/docs/instagram-platform/content-publishing

## 7. Tokens

- **Fato (Instagram Login):** Token de curta duração expira em 1 hora. — Fonte: https://developers.facebook.com/docs/instagram-platform/reference/access_token/ (trecho: "expire in one hour")
- **Fato (Instagram Login):** Troca de curto para longo prazo via `GET https://graph.instagram.com/access_token`, resultando em token de longa duração válido por 60 dias. — Fonte: https://developers.facebook.com/docs/instagram-platform/reference/access_token/ (trecho: "long-lived Instagram User access token that expires in 60 days")
- **Fato (Instagram Login):** Refresh do token de longa duração via `GET https://graph.instagram.com/refresh_access_token` com `grant_type=ig_refresh_token`; o token renovado passa a valer por mais 60 dias a partir da data de renovação. **Verificado em 2ª rodada**, WebFetch direto em https://developers.facebook.com/docs/instagram-platform/instagram-api-with-instagram-login/business-login: três condições citadas literalmente: "The existing long-lived access token is at least 24 hours old"; "The existing long-lived access token is valide (not expired)" [sic, erro de digitação da própria doc da Meta]; "The app user has granted your app the `instagram_business_basic` permission". Também confirmado nessa mesma página: token curto "valid for 1 hour and can only be used once"; token longo "valid for 60 days".
- **Fato (novo, 2ª rodada):** A doc oficial consultada **não diferencia** o ciclo de vida do token quando emitido para o dono/admin do app em modo Development versus outros usuários — o texto trata todos os usuários com o mesmo fluxo de emissão/refresh. — Fonte: https://developers.facebook.com/docs/instagram-platform/instagram-api-with-instagram-login/business-login (verificado em 2ª rodada, WebFetch direto).
- **Fato (Facebook Login, verificado em 2ª rodada):** WebFetch direto em https://developers.facebook.com/docs/facebook-login/guides/access-tokens/get-long-lived confirma: "A long-lived token generally lasts about 60 days" para o user access token; e "Long-lived Page access token do not have an expiration date and only expire or are invalidated under certain conditions" para o Page access token obtido a partir de um long-lived user token. Ou seja, **confirmado oficialmente**: user token ~60 dias, Page token sem expiração fixa (só invalida sob certas condições, ex.: troca de senha, revogação, app removido).

## 12. Rate limit (BUC)

- **Fato — Verificado em 2ª rodada** (WebFetch direto em https://developers.facebook.com/docs/graph-api/overview/rate-limiting): a fórmula oficial da seção "Instagram Platform" do BUC Rate Limit é literalmente "Calls within 24 hours = 4800 * Number of Impressions", onde "Number of Impressions is the number of times any content from the app user's Instagram professional account has entered a person's screen within the last 24 hours".
- **Fato — Verificado em 2ª rodada:** o header de resposta relevante para monitorar o uso do BUC é `X-Business-Use-Case-Usage`, que "can return up to 32 objects in one call" e traz métricas como `call_count`, `total_cputime` e `total_time` expressas como percentuais do uso permitido. (O header `X-App-Usage`, mais genérico do Graph API, não foi confirmado literalmente nesta página para o caso específico do Instagram Platform.)
- **Fato — Verificado em 2ª rodada:** a mesma página nota que "Business Discovery and Hashtag Search API are subject to Platform Rate Limits" — ou seja, essas duas APIs específicas (não usadas neste piloto) seguem um limite diferente do modelo por impressões/24h.
- **Fato:** Para uma conta pequena como a da pastoral (poucos seguidores, 2 posts/semana), esse cálculo baseado em impressões tende a resultar num teto baixo de chamadas — mas ainda assim muito acima do necessário para 2 publicações semanais + coleta de métricas ocasional.
- **NÃO VERIFICADO mesmo após 2ª rodada:** o limite alternativo, mais citado por terceiros, de "200 chamadas por usuário por hora" — não apareceu no texto extraído da página oficial de rate limiting consultada (que descreve exclusivamente o modelo por impressões/24h para o Instagram Platform). Pode se referir a uma limitação diferente (Graph API geral / Marketing API) e não deve ser assumido como aplicável ao Instagram Platform sem nova confirmação.

## Implicações para o projeto

- Como Diogo é dono/admin único da conta e do app, o cenário mais simples é **Instagram API with Instagram Login**, sem exigir Página do Facebook, evitando a complexidade de vincular a conta a uma Página caso ela ainda não esteja vinculada.
- Com **Standard Access** e Diogo com papel de admin no app, **App Review não deve ser necessário** para este piloto — reduz drasticamente o tempo até publicar via API. Atenção: a 2ª rodada não confirmou o papel/caminho exato de "Instagram Tester" na doc genérica de App Roles (ver riscos, item 7) — como Diogo provavelmente será o próprio dono/admin do app (não um terceiro convidado como tester), isso não deve bloquear o piloto, mas vale checar no próprio App Dashboard ao criar o app.
- Legenda: respeitar limite confirmado de **2.200 caracteres, 30 hashtags e 20 @menções** no campo `caption` (não suportado em itens individuais de carrossel). `alt_text` tem limite de **1000 caracteres** e não é suportado em Reels/Stories — pode reforçar a acessibilidade dos posts de imagem/carrossel da pastoral. `location_id` não é suportado em itens de carrossel.
- É preciso confirmar antes de codar: (a) se a conta @pastoraldodizimo.arquifln já está configurada como conta profissional (Business/Creator) — pré-requisito obrigatório para qualquer uma das duas variantes; (b) faixa de proporção/tamanho de imagem exata para gerar as artes já no formato certo (pesquisa adicional recomendada antes de fixar o pipeline de geração de imagem).
- O fluxo de publicação (imagem única e carrossel) segue sempre: criar container(s) em `/media` → checar `status_code` até `FINISHED` → publicar em `/media_publish`. Isso deve ser refletido no script Python do GitHub Action, incluindo tratamento de `ERROR`/`EXPIRED`.
- **Não há agendamento nativo** — o GitHub Action (via cron do workflow) é responsável por disparar a publicação no horário certo; não existe endpoint da Meta para "publicar às 18h de sexta-feira" de forma passiva.
- O limite de 100 posts/24h e o rate limit por impressões (BUC) são folgados para 2 posts/semana — não é um risco operacional relevante no piloto.
- Tokens de curta duração (1h, Instagram Login) devem ser trocados imediatamente por um de longa duração (60 dias) e o GitHub Action deve implementar rotina de refresh periódico (ex.: semanal) antes de o token completar 60 dias, respeitando a janela de "token com pelo menos 24h de idade" para poder ser renovado — isso precisa ser confirmado com fetch direto antes de implementar (ver riscos, item 4).
- Para coleta de métricas, `reposts`, `saved`, `shares`, `total_interactions`, `views`, `reach`, `likes`, `comments` estão disponíveis para posts (FEED); `impressions` só serve para mídia publicada antes de 02/07/2024, então não deve ser usada como métrica principal do pipeline de métricas.
- Antes de decidir entre Instagram Login e Facebook Login definitivamente, é necessário fechar os pontos NÃO VERIFICADOS de tokens do Facebook Login (item 5) e confirmar se a conta já está ou não vinculada a uma Página do Facebook — isso muda a escolha da variante.
- Recomenda-se uma segunda rodada de pesquisa focada e pontual (fetch direto, não busca) nas 4-5 lacunas da seção de riscos antes de codar o script de publicação, para não basear decisões de dimensionamento de imagem/legenda em suposições.
